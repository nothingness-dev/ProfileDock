# ProfileDock Threat Model

Review date: 2026-08-22

This document describes ProfileDock's local security boundary, the threats considered by the project, the controls implemented, and the risks that remain. It is a design review, not a claim that ProfileDock provides a hardened browser sandbox or protection against a compromised operating-system account.

## Scope and protected assets

ProfileDock protects operations performed by its CLI and controller around:

- Chromium profile data, including cookies, sessions, LocalStorage, cache, and login state.
- Profile metadata and metadata backups.
- Runtime state and local controller commands.
- Backup archives, restore staging areas, migration sources and destinations, and repair operations.
- Diagnostic logs generated by ProfileDock.

The configured data root is the primary filesystem boundary. ProfileDock expects each profile at `profiles/<id>/browser-data`, runtime state at `runtime/<id>`, metadata under `metadata`, logs under `logs`, and backups under `backups`.

## Trust boundaries and attacker model

ProfileDock treats these inputs as untrusted:

- Backup archives supplied to `restore`.
- Legacy projects supplied to `migrate`.
- Metadata and runtime files that are malformed, stale, or unexpectedly modified.
- Profile names, URLs, browser diagnostics, and other strings that may reach logs.
- Filesystem paths supplied through CLI options or environment variables.

ProfileDock is designed to resist malformed input, accidental corruption, interrupted operations, path redirection, PID reuse, and unauthenticated controller commands from ordinary local processes that cannot read ProfileDock's private runtime files.

ProfileDock does not defend against:

- Malware or another process running as the same OS account with permission to read or modify the data root.
- An administrator, root user, kernel-level attacker, debugger, or process-injection capability.
- A compromised browser, browser extension, website exploit, or Chromium vulnerability.
- Physical access, unencrypted disks, filesystem snapshots, cloud-sync copies, or backups outside ProfileDock's control.
- Denial of service through disk exhaustion, process exhaustion, or forced termination of ProfileDock at arbitrary machine-instruction boundaries.

## Threat review

### Malicious archives

Protections:

- Restore requires a recognized manifest and validates profile IDs, timestamps, engines, launch configuration, file paths, sizes, and SHA-256 values.
- Absolute paths, `..` traversal, Windows separator and alternate-stream forms, links, non-file/non-directory members, duplicate members, unlisted files, and manifest mismatches are rejected.
- Manifest size, individual member size, total uncompressed bytes, and archive member count are bounded.
- Files are extracted into a private temporary directory with exclusive creation, then verified before finalization.
- Existing profiles are quarantined only after conflict and active-state checks.

Residual risks:

- SHA-256 verifies archive consistency, not authenticity. An attacker who can rebuild an archive can also generate matching checksums.
- Archives are not signed or encrypted and may expose browser data to anyone who can read them.
- Size and member limits reduce resource abuse but cannot guarantee protection from all decompression CPU, memory, or disk-exhaustion attacks.
- Only restore archives from a trusted source when profile confidentiality or authenticity matters.

### Runtime-state spoofing

Protections:

- Runtime state is stored outside `browser-data`, written atomically, and owner-restricted on POSIX systems.
- Profile IDs, state shape, timestamps, controller tokens, ports, and process fields are validated before use.
- Malformed or ambiguous runtime state fails closed for destructive mutation.
- Direct and Playwright active-state checks use engine-specific verification instead of trusting a generic PID field.
- Runtime state is excluded from profile backup archives.

Residual risks:

- A same-account attacker who can read and rewrite `runtime/<id>/running.json` can forge structurally valid state and may cause denial of service.
- Runtime state is coordination data, not a cryptographically authenticated ledger.
- On Windows, confidentiality depends on inherited ACLs for the selected data root.

### PID reuse and accidental system process termination

Protections:

- Direct Engine records the browser PID and process creation time.
- A Direct Engine launch fails and stops the spawned browser if process identity cannot be recorded.
- Status and close operations compare the current process creation time with the recorded value.
- ProfileDock refuses to signal malformed or unverified Direct Engine state.
- A recycled PID with a different creation time is treated as stale and is never terminated by ProfileDock.

Residual risks:

- Process identity relies on operating-system process information and its availability and accuracy.
- A same-account or privileged attacker able to rewrite runtime state with a target PID and matching creation time is outside the protection boundary.
- ProfileDock cannot prevent another program or the user from terminating unrelated processes independently.

### Local controller command injection

Protections:

- The Playwright controller listens only on loopback and accepts a bounded command vocabulary for lifecycle, tab inspection, navigation, page reading, JavaScript evaluation, and cookie export.
- Each controller uses a random per-launch token stored in private runtime state.
- Commands have size limits and socket timeouts, and tokens are compared in constant time.
- Commands and arguments are schema-checked, URLs are restricted to supported schemes, and request and response sizes are bounded.
- `eval` intentionally executes the exact JavaScript expression supplied by the local CLI user inside the selected page. It never executes that expression as a shell command or Python expression.
- Mutation checks can authenticate controller availability before changing profile data.

Residual risks:

- The token is a bearer credential. A same-account attacker who can read runtime state can send valid commands.
- A token holder can execute JavaScript in the profile's pages and export live cookies for the controller lifetime; these capabilities are equivalent to controlling that browser session.
- Tokens remain valid for the controller lifetime and do not provide replay protection.
- Loopback does not establish OS-user identity by itself.
- The protocol provides local command authentication, not encryption or protection from a privileged packet/process observer.

### Symlink and junction escape

Protections:

- Destructive targets are resolved and checked against the configured root before use; targeting the root itself is rejected.
- Profile IDs are validated before path construction.
- Lexical traversal and resolved-path escapes are rejected.
- Existing path components and directory trees are checked for symbolic links, Windows junctions, and reparse points.
- Delete, restore, migration removal, and repair cleanup validate trees before recursive removal.
- Tests exercise Unix symbolic links and Windows junctions where the platform permits them.

Residual risks:

- Filesystem checks and mutation are separate system calls, so a hostile same-account process may attempt time-of-check/time-of-use races.
- ProfileDock reduces this risk with private directories, exclusive temporary files, same-parent atomic renames, and repeated validation, but Python does not provide a portable race-free directory capability API across all supported platforms.
- Filesystems or network mounts with unusual link, case, or rename semantics may not provide the same guarantees as local NTFS, APFS, ext4, or similar filesystems.

### Metadata corruption

Protections:

- Metadata has a versioned schema and strict validation for IDs, timestamps, engines, duplicate IDs, duplicate directories, and exact managed data paths.
- Writes use a cross-process lock, private unique temporary file, flush and `fsync`, and atomic replacement.
- The previous metadata version is copied to a separate backup before updates.
- Unsupported, malformed, or unsafe metadata is rejected rather than silently overwritten.
- `doctor --repair` restores only metadata that passes the same validation.

Residual risks:

- The backup is a local recovery copy, not an independent or immutable backup.
- Simultaneous damage to the primary file and backup requires manual recovery.
- Metadata is not signed; a same-account attacker can replace it with another structurally valid document that remains inside the data root.
- Filesystem or storage-device failure can defeat atomicity guarantees supplied by the operating system.

### Interrupted operations

Protections:

- Backup output, metadata writes, restore, migration, deletion, and source removal stage changes before commit.
- Restore and deletion quarantine replaced directories and restore them when a pre-commit step fails.
- Migration copies into temporary directories, verifies complete file manifests, detects source changes, and rolls back incomplete destination changes.
- Source removal stages tracked source entries through same-parent renames and rolls them back if staging fails.
- Doctor can identify and safely clean recognized stale temporary and quarantine directories under the data root.

Residual risks:

- Power loss, kernel failure, disk failure, or forced termination during the final rename/cleanup window can leave a recoverable quarantine or temporary directory.
- Cleanup failure after a committed operation may leave extra private files that require `doctor --repair` or manual review.
- ProfileDock does not provide a general journal, multi-disk transaction, or crash-consistent guarantee for filesystems that do not honor atomic rename and `fsync` semantics.

### Sensitive logging

Protections:

- ProfileDock does not intentionally log cookies, passwords, LocalStorage values, controller tokens, or authorization header values. Explicit cookie exports are written only to the requested output stream or private atomic JSON file.
- URLs are reduced to origin and a limited path prefix without query strings or fragments.
- Known secrets, common credential fields, and bearer tokens are redacted before structured log writes.
- Log messages and controller diagnostics are bounded, runtime tokens receive explicit redaction, and logs rotate by size.

Residual risks:

- Redaction is best effort and cannot recognize every secret format or sensitive value embedded in arbitrary names, paths, browser messages, or exception text.
- Logs may expose profile IDs, profile names, browser executable paths, local usernames contained in paths, event timing, PIDs, and sanitized origins.
- Anyone who can read the data root may be able to read logs.
- Users should inspect logs before sharing them and should not place secrets in profile names, paths, or CLI arguments.

### Local OS-account access

Protections:

- On POSIX systems, ProfileDock creates managed directories with owner-only permissions and private state files with mode `0600`.
- Runtime state, logs, metadata, backups, and browser data are separated to reduce accidental exposure and unsafe cross-use.
- Controller authentication prevents an unrelated local process from issuing valid commands unless it obtains the token.
- Profile data roots, temporary files, and metadata are kept out of the project directory by default.

Residual risks:

- ProfileDock's primary trust boundary is the OS account. A process with the same account permissions can generally read cookies, sessions, archives, logs, metadata, and controller tokens.
- Windows protection depends on inherited ACLs; ProfileDock does not create a custom access-control list.
- Administrator/root access, backup operators, endpoint security software, cloud-sync software, and disk-access tools may bypass application-level controls.
- Use a separate OS account, full-disk encryption, and appropriate filesystem permissions when stronger local isolation is required.

## Security properties ProfileDock does not provide

ProfileDock does not provide password management, credential encryption, archive signatures, archive encryption, browser sandboxing, malware isolation, website isolation beyond separate Chromium user-data directories, secure deletion, anti-forensics, network anonymity, proxy isolation, or protection from a compromised OS account.

Profile separation prevents normal Chromium state from being shared through the same user-data directory. It does not guarantee that websites, extensions, browser synchronization, downloaded files, the clipboard, DNS, the network, or the operating system cannot correlate or exchange information across profiles.

## Operational recommendations

- Keep ProfileDock and browser dependencies updated.
- Keep the data root on a local filesystem with permissions restricted to the intended OS account.
- Use full-disk encryption when profile confidentiality matters.
- Treat backup archives as sensitive credential-bearing data.
- Restore and migrate only from trusted sources, even though inputs are validated.
- Close profiles before backup, restore overwrite, migration, deletion, or repair.
- Run `profiledock doctor` after a crash or interrupted filesystem operation.
- Review logs before sharing them.
- Maintain independent backups of important profiles and verify recovery periodically.

## Review and verification

Security behavior is covered by tests for malicious archive paths and member types, archive resource limits, metadata traversal, corrupted metadata, symlink and junction escapes, transactional rollback, stale and spoofed runtime state, PID reuse, controller command size and authentication, controller availability probing, and sensitive-data redaction.

This threat model should be reviewed whenever archive formats, controller commands, process management, data-root layout, logging fields, or filesystem mutation behavior changes.
